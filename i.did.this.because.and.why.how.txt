HOW UPSTREAM TAKES PATCHES
--------------------------
OpenVPN does not merge GitHub PRs (see .github/PULL_REQUEST_TEMPLATE.md
and CONTRIBUTING.rst): send to openvpn-devel@lists.sourceforge.net with
git send-email (subject "[PATCH] ..."), or use gerrit.openvpn.net.
Every commit needs your Signed-off-by: line; none of these commits has
one. Code style: clang-format with the repo's .clang-format (needs
clang-format >= 20; Ubuntu's 18 cannot read it). All commits pass
"git clang-format --diff master".

HOW EVERYTHING WAS TESTED
-------------------------
- Build: autotools with --enable-werror, no warnings. CMake
  (-DUNSUPPORTED_BUILDS=ON -DENABLE_PKCS11=OFF): 19/19 ctest pass.
- Unit tests: 19/19 drivers pass (make check); two new drivers,
  test_dns (17 cases on this branch) and test_env_set.
- AddressSanitizer + UBSan build (whole tree): 19/19 unit test drivers
  pass with no sanitizer report; the PUSH_UPDATE scenarios of 01 and 02
  run end to end with the sanitized binary as server and client, with
  no report either.
- Windows: dns.c, options.c, tun.c, push.c, init.c, env_set.c compile
  with mingw-w64 (-fsyntax-only, a hand-made config.h).
  Android: options.c/dns.c/tun.c with -DTARGET_ANDROID (-fsyntax-only).
  Neither was run on a device.
- End to end on Linux: an OpenVPN server and a client (client in its
  own network namespace, veth link, real tun devices), built from this
  tree and from master, with logging --up / --dns-updown scripts and
  PUSH_UPDATE sent via the management interface (push-update-cid).
  Every scenario of every note was run against master (to see the bug)
  and against the fix; the combined branch re-ran all of them with the
  same results as the separate branches.
- "Old client" simulation for 07: master built without the
  IV_PROTO_DNS_OPTION_V2 line.


THINGS SEEN WHILE TESTING, NOT FIXED (separate issues)
------------------------------------------------------
1. Server: a PUSH_UPDATE sent with push-update-cid while the link is
   idle is logged as "SENT CONTROL" but only goes out with the next
   event for that client (e.g. a keepalive ping). Without --keepalive,
   the second of two updates never arrived during a 10 s test.
2. Client with --user/--group: ANY PUSH_UPDATE (also e.g. a "route"
   one) makes the client exit: do_update() force-closes and reopens the
   tun device, which fails as the unprivileged user ("Cannot open
   TUN/TAP dev /dev/net/tun: Permission denied ... Exiting due to fatal
   error"). Same on master.
